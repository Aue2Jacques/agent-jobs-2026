# E1：三家常见 harness 的流式故障小实验（2026-10-05）

> 目的：验证 [project-direction.md](../project-direction.md) 第九节的假设——**在最新版的常见 harness 上，用故障注入至少能复现 3 类故障，其中至少 1 类是"假成功"。**
> 结论：**假设成立**，但复现出的 bug 基本都已经有人报过（还开着），"找新 bug"这个卖点比预想弱。
> 花费：0 元（全程用模拟的模型服务，不调真实模型）；耗时约 1.5 小时；在开发机上跑。
> 脚本和原始结果：`experiments/E1-stream-faults/`

## 一、做法

- **被测对象**（都是 npm 上 10-05 的最新版）：Claude Code 2.1.289、Codex CLI 0.160.0、OpenCode 1.18.34。都用无界面模式（`claude -p`、`codex exec`、`opencode run`），各自用隔离的配置目录，模型服务地址指向本机。
- **模拟的模型服务**：
  - 第一轮用 aimock 1.43.0 的现成 fixture（9 个场景）。
  - 第二轮用自己写的 150 行原始流服务 `rawsse.py`（4 个场景），专门测 aimock 表达不了的故障。
- **判定**：看退出码、最终输出、模拟服务收到了几次请求（判断有没有重试）、耗时、有没有执行工具命令（看工作目录里有没有标记文件）。每个场景限时 5 分钟，"卡住"类限时 12 分钟。
- **每个场景只跑 1 次**。判定依据的都是确定性的行为（退出码、请求次数），不是概率性的，但没有多次运行。

## 二、结果

✅ 处理正确 ❌ 有问题 ⚠️ 有争议 — 作废

| 场景（模拟服务做了什么） | Claude Code | Codex | OpenCode |
|---|---|---|---|
| 基线：正常回复 | ✅ | ✅ | ✅ |
| **空回复**：200，内容为空，正常结束 | ⚠️ 追问 1 次后仍以成功结束，结果为空，退出码 0 | ⚠️ 没重试，空消息，退出码 0 | ⚠️ 没重试，没有文本，退出码 0 |
| **空内容 + 因长度截断结束** | ✅ 重试 3 次后报错；但报错写的是"超出 64000 输出 token 上限"，实际输出 0 个 token，诊断不对 | 第一轮作废（aimock 发错了事件）；第二轮用真实事件重测：✅ 重连 5 次后报错 | ❌ 退出码 0，结束原因是 length 但没有任何文本，当成功处理（对应还开着的 #50949） |
| 流发到一半断开 | ✅ 流式重试约 3 分钟后改用非流式请求，拿到完整回复 | ✅ 重连 5 次后报错 | ✅ 重试约 69 秒后报错 |
| 第一次 500，第二次正常 | ✅ | ✅ | ✅ |
| 正常工具调用 | ✅ | ✅ | ✅ |
| 工具参数 JSON 不完整，但正常结束 | ✅ 不执行 | ✅ 不执行（解析错误反馈给模型） | ✅ 不执行（记为无效工具） |
| 工具参数发到一半断开 | ✅ 重试，改非流式后执行完整命令 | ✅ 报错 | ✅ 报错 |
| **连响应头都不发** | ✅ 约 6 分钟超时后重试 | ❌ 12 分钟里只发了 1 次请求，一直干等，不超时（对应还开着的 #50775） | ✅ 约 5 分钟超时后重试 |
| **干净收尾，但没有结束标记**（第二轮） | ✅ 改非流式后报错，104 秒 | ✅ 重连 5 次后报错 | ❌ **死循环：300 秒内发了 2001 次请求**，每次都把半截回复当成一步，"结束原因未知"就继续下一步，没有退避也没有上限（对应还开着的 #49414、#43939、#45315） |
| 真实的"因长度截断"事件（第二轮） | ✅ 报错（同上，诊断文字不对） | ✅ 重连 5 次后报错 | — 我的脚本写错了，作废（第一轮已覆盖） |
| 开始发了一点后卡住（第二轮） | ✅ 约 5 分钟后改非流式 | ✅ 约 5 分钟空闲超时，重连 | ✅ 约 5 分钟超时，重试 |
| **只发保活包，不发内容**（第二轮） | ⚠️ 把保活包当作有进展，约 10 分钟后改非流式 | ⚠️ 不把保活注释当进展，5 分钟断开重连 | ❌ 12 分钟里只发了 1 次请求，一直挂着，不超时（对应还开着的 #43519） |

关于"空回复"标 ⚠️：协议上空回复是合法的，但在无界面运行时，"退出码 0、结果为空"会让自动化流程以为任务完成了。三家的用户都报过这个问题（OpenCode #37735、Codex #32389、Claude Code #93419），而且都还开着。

## 三、和假设对照

| 第四节的故障类 | 复现了吗 |
|---|---|
| ① 空回复被当成正常完成 | 复现：三家都是；OpenCode 连"因长度截断的空回复"也当成功 |
| ② 没有结束标记 | 复现：OpenCode 死循环 |
| ③ 空闲看门狗 | 复现：Codex 不发响应头时不超时；OpenCode 只收到保活包时不超时 |
| ④ 工具参数截断 | 没复现：三家都处理正确 |
| ⑤ 重试策略 | 没复现：三家都会重试，Claude Code 还会改用非流式 |

**5 类里复现 3 类，三家都有"假成功"，假设成立。**

## 四、意外的发现

1. **复现出的 bug 几乎都已经有人报过**：OpenCode 的 4 个问题、Codex 的 1 个问题都能找到对应的 issue，而且都还开着。可能没人报过的只有一个：Claude Code 输出 0 个 token 时，却报"超出 64000 输出 token 上限"。所以"我发现了 X 个新 bug"这个说法撑不起来，更现实的说法是"系统地复现、量化，然后修掉"。
2. **OpenCode 的问题最集中**，5 个场景里有 4 个出问题；它也是三家里唯一能直接提修复的开源项目（Codex 也开源，但它的问题只有 1 个）。
3. **aimock 本身有 5 处不够用**（这正是二开要补的）：
   - 不设块间延迟时，"发到第 N 块断开"实际一个字节都没发出去；
   - 在 Responses 协议下，"因长度截断"发成了 `response.completed` 事件，真实接口是 `response.incomplete`，所以 Codex 第一轮的结果作废；
   - 它的延迟加在响应头之前，模拟不了"开始发了一点后卡住"；
   - 表达不了"干净收尾但没有结束标记"和"只发保活包"；
   - 故障只对流式请求生效，harness 改用非流式请求就绕过去了（Claude Code 就是这样恢复的）。
4. **我自己差点误判一次**：第一眼看到 Claude Code 在"流发到一半断开"时返回了成功，还执行了被截断的工具命令。查了模拟服务的请求日志才发现，它是流式失败 11 次后改用非流式请求，拿到了完整内容，处理是正确的。教训：判定要看请求日志，不能只看最终输出。

## 五、局限

- 每个场景只跑 1 次；只测了三家；只测了无界面模式，交互界面里的表现可能不同。
- 模拟服务只是近似。比如真实的 Anthropic 接口在非流式请求时也可能出同样的故障，我们的服务对非流式要么返回 500，要么一直挂着。
- "保活包算不算进展"没有标准答案：算的话，卡死的流会挂很久；不算的话，模型思考时间长就会被误杀（OpenClaw #152535 抱怨的就是后一种）。

## 六、对选题的影响 [推断]

- 方向站得住：最新版里确实有没修的问题，而且只靠 harness 的代码才能解决，换更强的模型没用。
- 讲法要改：重点从"找新 bug"改成"**修 OpenCode 的 Agent Loop 终止判定**"。它有一串还开着的 issue（#49414、#43939、#45315、#50949、#43519 等），根源是同一处逻辑：怎么判断"这一步结束了、该继续、该重试还是该报错"。修好以后，用这套故障注入当回归测试，正好对应面试里"Agent Loop 停止条件""怎么证明有效"这两个问题。
- aimock 的 5 处不足可以作为第二部分贡献，提给上游。
