# E2：把 E1 整理成可复用的工具 harnessprobe v0（2026-10-05）

> 目的：把 E1 里的一次性脚本整理成"一家 harness 一个适配器、场景只写一次"的结构，验证重构后结果和 E1 一致。
> 结论：**一致**。全部 38 个"harness × 场景"组合重跑了一遍，除了 E1 里本来就作废的两项，判定都和 E1 相同。另外改掉了 3 处判定规则和 1 处运行器的问题。
> 花费：0 元；全程在开发机上跑，约 45 分钟。

## 一、工具结构

见工具自带的 README。要点：
- `adapters/`：每家 harness 一个适配器，回答四个问题：怎么启动、说哪种协议、工具怎么对应、怎么读结果。三家的适配器各 40–60 行。
- `scenarios.py`：场景只用通用动作写一次，比如"执行命令"。适配器负责翻译成各家的工具名和参数名：Claude Code 是 `Bash.command`，Codex 是 `exec_command.cmd`，OpenCode 是 `bash.command`。
- `runner.py`：启动模拟服务，在隔离目录里跑 harness，统计请求次数，然后自动判定。
- 判定结果分为：通过、假成功、重试风暴、卡死、慢速重试、执行了不合法的调用、没执行。

## 三、重构过程中改掉的问题

1. **OpenCode 认环境变量 `PWD`，不认进程实际所在的目录**。运行器原样继承了父进程的 `PWD`，命令就被执行到了上一级目录，于是"正常工具调用"被误判成"没执行"。这是运行器的问题，不算 OpenCode 的 bug，因为正常的 shell 都会设好 `PWD`。已在运行器里显式设置。
2. **"工具参数发到一半断开"的判定太粗**。Claude Code 改用非流式请求后执行了完整命令，这是正确恢复，原规则却判成了假成功。现在改为：执行的是完整命令，并且后续回复正常，就算通过。
3. **"重试风暴"要先于"超时"判定**。否则 OpenCode 的死循环会因为同时超时而被判成"慢速重试"。
4. **请求计数要排除标题生成之类的附带请求**。OpenCode 每次运行都会额外发一个不带工具的标题请求。现在只统计带工具定义的主循环请求，"只发保活包"一项因此从"慢速重试（2 次）"更正为"卡死（1 次）"。

前三条是判定和运行器的问题，第四条是计数口径。四条都说明一件事：**判定规则本身要用真实运行去校准**，不能只在纸上设计。
