# 第一批测试场景和判定标准（2026-10-05）

> 目标：练出一套能接到**任意 harness（包括公司内部的闭源 harness）**上找问题的方法和工具。
> 本文是第一步：读透公开的真实 bug，定下"往 harness 里注入什么"和"怎么判断它处理得对不对"。还没写代码。
>
> 依据：
> - [FSE '26 公开数据集](https://zenodo.org/records/18342487)：Claude Code、Codex、Gemini CLI 共 3864 个已关闭的 bug，带人工标注的根因。我挑出其中 21 个根因子类，共 1389 个 issue，用 GitHub 接口拉了标题和正文开头，**标题全部人工读过一遍**。
> - 港科大 [2607.15684](https://arxiv.org/abs/2607.15684) 的 8 类"模型行为触发的 harness bug"。
> - 我们自己的 E1 小实验。

## 一、读完的结论

1. **能用模拟服务复现的 bug 比预想的多**：凡是触发点是"模型服务返回了什么"的 bug，都能在不调用真实模型的情况下复现。返回内容包括正常回复、工具调用、报错、流的形态。
2. **最大的一类，E1 完全没测到**：harness **发出去的请求本身不合法**。比如用户中断、工具出错之后，对话历史里留下"有工具调用、没有工具结果"的残缺记录，下一次请求被真实接口以 400 拒绝，会话从此用不了。仅 Claude Code 就有 87 个这类 issue。E1 的模拟服务来者不拒，所以漏掉了。
3. 因此最重要的判定方式是：**让模拟服务像真实接口一样，严格校验 harness 发来的每一个请求**。这种检查是确定性的，不需要模型，而且对任何 harness 都适用。

## 三、五种判定方式

同一套判定方式对所有 harness 适用，这是"可迁移"的关键。

| 编号 | 判定方式 | 判什么 | 怎么实现 |
|---|---|---|---|
| O1 | **请求合法性** | A 类：harness 发出的请求能不能被真实接口接受 | 模拟服务对每个请求做真实接口会做的校验：工具调用和结果一一配对、没有空内容块、是合法的 UTF-8 和 JSON、思考块原样带回、工具名和 Schema 合规、推理条目顺序正确。不合法就记录下来，并像真实接口一样返回 400 |
| O2 | **如实报告结局** | 有没有"假成功" | 看退出码和最终输出：故障发生了却退出码 0、结果为空或是半截，就判为假成功 |
| O3 | **重试行为** | B、C 类 | 请求次数、间隔、是否遵守 Retry-After、有没有上限（E1 里 OpenCode 300 秒发了 2001 次就是反例） |
| O4 | **工作区核对** | D 类：模型要求的操作有没有被原样执行 | 让模型下发的命令把结果写进文件，再逐字节核对；被截断或非法的调用必须**没有**执行 |
| O5 | **时限** | 卡死 | 在规定时间内结束；超时就判为卡死 |

## 四、第一批场景（15 个）

挑选原则：真实 bug 多、能确定性复现、三家（Claude Code、Codex、OpenCode）都能跑。

| # | 场景：模拟服务注入什么 | 判定 | 对应原型 |
|---|---|---|---|
| S1 | 模型调用一个会失败的命令（命令不存在 / 超时），看下一轮请求 | O1：工具结果要配对 | A1 |
| S2 | 模型一次返回 3 个并行工具调用，其中 1 个失败 | O1 | A1 |
| S3 | 返回空回复，然后让 harness 继续下一轮（比如追问一次） | O1：下一轮不能带空内容块；O2 | A2、D1 |
| S4 | 工具输出里放大量 emoji，长度正好跨过 harness 的截断上限 | O1：下一轮请求体必须是合法 UTF-8/JSON | A3 |
| S5 | 返回带签名的思考块，同时调用工具 | O1：下一轮要原样带回思考块；Responses 协议下推理条目顺序正确 | A4 |
| S6 | 连续返回 3 次 529/500，第 4 次正常 | O3：会重试且有退避；O2：最终成功 | B1 |
| S7 | 返回 429，带 `Retry-After: 20` | O3：至少等 20 秒，不崩溃 | B2 |
| S8 | 返回"上下文超限"错误（各协议的真实错误格式） | O3：压缩或截断后重试，不能无限循环；O2 | B3 |
| S9 | E1 的 5 种流故障：中途断开、没有结束标记、开始后卡住、只发保活包、不发响应头 | O2、O3、O5 | C |
| S10 | 空回复；因长度截断的空回复 | O2 | D1 |
| S11 | 工具参数是非法 JSON；调用不存在的工具；缺必填参数 | O4：不执行；O3：不陷入死循环 | D2 |
| S12 | 命令里含引号、`$`、`!`、管道、带空格的路径、多行 | O4：实际执行的命令和模型给的完全一致 | D3 |
| S13 | 编辑一个 CRLF 文件、一个制表符缩进的文件、一个含中文和 emoji 的文件、一个含 `%` 的文件 | O4：编辑后的文件逐字节等于预期 | D4 |
| S14 | 返回拒答（Anthropic 的 `stop_reason: refusal`、OpenAI 的 `content_filter`） | O2：如实报告，不能当成功 | D5 |
| S15 | 正常工具调用加正常回复（基线） | 全部判定都应通过 | — |

E 类（中断、恢复）和 A5（工具定义）放到第二批：前者要模拟用户中断进程再恢复，后者要配置 MCP 服务器，接入比较麻烦。

## 五、"一家 harness 一个适配器"

接入一家新 harness（包括公司内部的），只需要写一个适配器，回答四个问题：

1. **怎么启动**：无界面运行的命令、隔离配置目录、把模型地址指向模拟服务的方法（环境变量还是配置文件）。
2. **说哪种协议**：Anthropic Messages、OpenAI Chat Completions，还是 OpenAI Responses。模拟服务和请求校验按协议切换。
3. **工具怎么对应**：场景只写通用动作，比如"执行命令 X""把文件 F 里的 A 换成 B""写文件"。适配器把它翻译成这家 harness 的工具名和参数格式：
   - Claude Code 是 `Bash` / `Edit`；
   - Codex 是 `exec_command` 和补丁格式的 `apply_patch`；
   - OpenCode 是 `bash` / `edit`。
4. **怎么读结果**：解析它的输出格式，取出退出码、最终文本、报错。

所以场景写一次，三家甚至十家都能跑，这也是面试时"给我你们的 harness，一天接上"的底气。

## 六、局限

- FSE 数据集只有已关闭的 bug，到 2025 年底为止；空回复这类 2026 年才多起来的问题，它覆盖不到，所以还要用 E1 和最近的 issue 补充。
- 关键词统计有误差。表里的数字只用来排优先级，不当结论用。
- 不是所有 bug 都能用模拟服务复现：界面、安装、登录、操作系统兼容这些占了 FSE 里一大半，不在本项目范围内。
